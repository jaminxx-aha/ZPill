# Release Builds

## Version Source

`pubspec.yaml` is the Flutter version source and must include a monotonic
Android/iOS build number:

```yaml
version: 1.0.0+1
```

`ohos/AppScope/app.json5` must keep the same marketing version. Increase its
`versionCode` for every HarmonyOS release, then run:

```bash
tools/check_release_config.sh
```

## CI Gate

`.github/workflows/ci.yml` runs on pull requests and pushes to `main`. It
checks release configuration, analyzes, runs the full test suite, builds an
Android debug APK, and uploads that APK as a short-lived artifact. CI does not
receive production signing keys and therefore never publishes a release.

## Android Release Signing

Release builds use a dedicated signing config only when all four values are
present:

```bash
export ANDROID_KEYSTORE_PATH=/absolute/path/to/release.jks
export ANDROID_KEYSTORE_PASSWORD='...'
export ANDROID_KEY_ALIAS='...'
export ANDROID_KEY_PASSWORD='...'
flutter build appbundle --release
```

For a local interactive build, the same keys may be placed in the ignored
`android/key.properties` file using `storeFile`, `storePassword`, `keyAlias`,
and `keyPassword`. Keep that file and the keystore outside version control.
Without the complete set, Gradle produces an unsigned release artifact and
never falls back to the debug key.

## HarmonyOS Signing

The tracked `ohos/build-profile.json5` intentionally has an empty
`signingConfigs` list. Local signing is injected by `ohos/hvigorfile.ts`, so the
shared build profile does not need machine-local paths or passwords.

Keep the non-secret signing material in `ohos/signing/local-signing.json`. The
whole `ohos/**/signing/` directory is ignored, and the file must not contain
password fields:

```json
{
  "name": "default",
  "type": "HarmonyOS",
  "material": {
    "storeFile": "/absolute/path/to/signing.p12",
    "keyAlias": "CHANGE_ME",
    "signAlg": "SHA256withECDSA",
    "profile": "/absolute/path/to/signing.p7b",
    "certpath": "/absolute/path/to/signing.cer"
  }
}
```

Store the encrypted password values generated by DevEco Studio in the macOS
Keychain. Leaving `-w` as the final argument makes `security` prompt without
putting the value in shell history:

```bash
security add-generic-password -U -a storePassword \
  -s com.jaminxx.nikon_pill.ohos-signing -w
security add-generic-password -U -a keyPassword \
  -s com.jaminxx.nikon_pill.ohos-signing -w
```

`hvigorfile.ts` reads those two Keychain items only during a local build and
combines them with the ignored signing material. On machines without the local
config it leaves signing unchanged. Do not put passwords in
`local-signing.json`, environment files, or any tracked file.

When replacing certificates, update `local-signing.json` and replace both
Keychain items:

```bash
security delete-generic-password -a storePassword \
  -s com.jaminxx.nikon_pill.ohos-signing
security delete-generic-password -a keyPassword \
  -s com.jaminxx.nikon_pill.ohos-signing
```

Signing material that has appeared in repository history must be treated as
exposed and rotated before distribution.
